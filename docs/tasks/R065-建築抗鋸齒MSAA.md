## 施工紀錄

- `post.ts`（受保護檔，Claude 改）：`Style` 多 `msaa`；`STYLE_A` 預設 4；`msaaSamples()` 取設定與顯示卡上限（WebGL2 `MAX_SAMPLES`）的較小值；`Pipeline.render()` 換完大小後確認取樣數，變了才把渲染目標重建一次。深度跟著解析（three.js 多重取樣渲染目標預設 `resolveDepthBuffer`），描邊照舊用深度。
- 先寫成「先確認取樣數、再換大小」，故意弄壞「換大小掉取樣」會被第一組先攔下（第一次畫一定會換大小），改成「先換大小、再確認取樣數」：換大小就算掉了取樣，同一幀會補回來，代價是多重建一次，守衛就紅在換大小那一句。
- **軟體繪圖不取樣**：第一版在本機全套瀏覽器守衛裡，`walls-browser` 超過它自己的 110 秒期限。量了每幀：本機 Chrome 是軟體繪圖（SwiftShader，沒有顯示卡時瀏覽器的備援，多邊形全靠 CPU），開 4 倍取樣萊伊 1440 寬每幀 80→99ms、412 寬 44→52ms，96 圖幾乎不變。真的顯示卡上取樣幾乎不花時間，軟體繪圖上卻是兩成，而且用軟體繪圖的玩家本來就卡。所以 `Pipeline` 第一次畫時讀一次 GL 的繪圖器名稱（Chrome 從 `WEBGL_debug_renderer_info` 讀真名），是 SwiftShader／llvmpipe 這類就不取樣。CI 的 Chrome 也是軟體繪圖，所以既有守衛在 CI 上的畫面跟 R065 之前逐位相同。
- `walls-browser` 的事後查證：關掉取樣後它在本機還是偶爾超時；同一台機器上 R060 那一版（`0e2b4e0`）也超時、main `725fb1f` 109.1 秒剛好過。這支守衛在本機（4 核）就壓在 110 秒線上，跟 R065 無關；CI 一直是綠的。

### 沒做成的事

- **細線會變淡**：建築上很細的深色木構線、窗格，原本在半解析度上是一整格深色（有時斷斷續續），開了取樣後跟牆色混成中間色，手機寬最明顯。這是取樣抗鋸齒本來的取捨；業主看圖覺得太淡，可以只改 `STYLE_A` 那一個數字把預設關掉（`?noR065=1` 現在就能關）。
- **沒有顯示卡的電腦／手機看不到抗鋸齒**：瀏覽器退回軟體繪圖時不取樣（理由見施工紀錄）。
- 只在本機 Chrome（軟體繪圖）量過；手機實機沒看，也沒量真顯示卡上的耗時。CI 的 Chrome 也是軟體繪圖，所以「預設真的有取樣」只有 Node 守衛（假的 GL 名稱）與強制開的 Chrome 畫面在驗。
- 描邊（深度跳變變暗）本身沒有抗鋸齒：深度只解析一個取樣，描邊仍是硬邊。
- 陰影仍是 `BasicShadowMap`（硬邊陰影），沒改成柔和陰影：那是光影的畫風，不在這張。
