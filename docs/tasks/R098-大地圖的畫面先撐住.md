## 為什麼做這張

R090（128×128 的海斯地圖）寫卡之後跑了卡面挑錯（工作流 wf_bc47d333-fd4，三個方向、每條找人推翻，確認 29 條）。其中畫面的三件今天的地圖就有，地圖變大只會更糟；而且三件都能做到**畫出來的像素逐位一樣**，所以照 R096（找目標）→R095、R097（尋路）→R090 的做法拆出來先做，R090 的畫面改動就只剩小地圖。

1. **進駐的單位換段那一幀很貴**：每一次房子換損壞階段（或鐵絲網、新房子、磨損、升起完成），`battle.ts:537`、`:707` 把**所有**單位的屋頂高度清掉；下一幀每個站在房子裡、霧裡看得到的單位（不只畫面上的）都對整鎮（河鎮約 7 萬個三角形、沒有空間索引）打一次射線，約 2–3 毫秒一個。挑錯時在 Node 量的整個換段那一幀（onEvents＋update＋render）：

   | 進駐的單位 | 0 | 1 | 4 | 8 |
   |---|---|---|---|---|
   | 河鎮（毫秒） | 11–13 | 16–17 | 25.5 | 32–38 |
   | 海斯原型（毫秒） | 11 | 18.5 | 27–30 | 40 |

   手機再慢三到四倍。一個單位的屋頂高度只跟它腳下那一棟有關；挑錯時比過「只對那一棟打」與「對整鎮打」，河鎮與海斯原型 4,554–5,718 個點 0 個不同。
2. **地面貼圖每次都整張上傳**：每一發高爆、每一次換損壞階段、每一棟新房子（`battle.ts:539`），以及**每一步有車在動**（`:1011`，最常見）都把整張地面貼圖送上顯示卡：河鎮 2.4 MB、128 圖 4 MB，這台筆電整張一次約 1.4 毫秒（含等顯示卡做完）。三 r186 的 `addUpdateRange` 一段只傳一列像素（`WebGLTextures.js:879–883` 寫死 height＝1；一段跨列會 GL 錯誤、整段沒傳），量到跟整張一樣貴；挑錯時量到改用 `renderer.copyTextureToTexture` 一個改過的格列傳一個矩形：兩支裝甲連一起動 0.20 毫秒（整張的 0.14 倍）、32 個全寬格列 0.45 毫秒（0.32 倍）。
3. **布陣時每點一下都整張重畫**：放一棟、拿掉一棟、復原都叫 `refreshPreview` → `setWorld`（`buildPlanner.ts:64`、`battle.ts:359`）：複製世界、整張地面重畫（帶地盤的色調）、整鎮重建。Node 量到河鎮 65–77 毫秒、海斯原型 102–110 毫秒，其中整張重畫 30–34／52–61 毫秒；這是玩家開新地圖做的第一件事，手機上一下約四分之一秒。

## 做什麼

1. **屋頂高度只重算改過的那一棟**（新檔 `src/render/roofCache.ts`；`battle.ts` 淨 0 行）：
   - `observerHeights` 每一筆多記它腳下那一棟的「樣子鍵」（R088 每棟一份快取用的鍵：段、磨損等級、是不是還在升起；`buildings.ts:565–590`）；讀的時候鍵不同才重打射線。
   - `battle.ts:537` 與 `:707` 的 `this.observerHeights.clear();` 拿掉（那兩行還在，淨 0）；換世界時（`:360`）照樣全部清掉。
   - `battle.ts:344`（對整鎮打射線那一行）一個字都不動：`tests/walls-view.mjs:37` 的 `garrison_ground` 錨著它、`:44` 要它唯一。所以重打的時候照舊對整鎮打，結果跟今天逐位一樣；省的是「不用每個人都重打」。
   - 鄰居的變化會不會影響（例如隔壁的瓦礫蓋過來）：守衛在每一次事件之後拿快取的值跟重新對整鎮打的比，有一點不同就紅（驗收 3）；真的有，鍵就加上鄰居。
2. **地面貼圖只傳改過的格列**（新檔 `src/render/groundUpload.ts`；`battle.ts` 淨 0 行）：
   - `paintCell` 把改過的格記到它那一格列的 [最小 x, 最大 x]；`render()` 裡每一個改過的格列上傳一個 8 像素高的矩形：`renderer.copyTextureToTexture(暫存, groundTex, 矩形, 位置)`。
   - 暫存是跟 groundTex 共用 `groundPx` 的 `DataTexture`；`sizeTo` 換了 `groundPx` 時暫存也重建。暫存永遠不畫、不 `initTexture`：三 r186 的 `WebGLRenderer.js` 在暫存已經上傳過時改走 GPU 複製（會從一張空貼圖複製過來）；沒傳過才是一次 `texSubImage2D(寬×高)`。
   - 部分上傳的那一幀不設 `groundTex.needsUpdate`（`setTexture2D` 會先整張傳）；`battle.ts:249`、`:364` 的 `needsUpdate = true` 原地換成上傳器的「整張」，整張之後、真的上傳之前加進來的格列不送（整張蓋過它們）；改過的格列超過 n/4、貼圖剛建好第一次上傳，都整張。上傳器每次都讀 `this.groundTex`，不存舊的貼圖。
   - 不用 `addUpdateRange`（見為什麼 2）。
3. **布陣預覽只重畫改到的格**（新檔 `src/render/previewDiff.ts`；`battle.ts` 淨 0 行）：
   - `setWorld` 換的是同一張圖、同一個 n、同一個染色的那一方時，新舊兩個世界逐格比地形、房子格、彈坑、植被、戰壕格、鐵絲網；改到的格再加一圈（路緣、戰壕接頭）重畫，再照第 2 項只傳那幾列。
   - 地圖、n 或染色的那一方不同時整張重畫（開局第一次預覽從 −1 換成我方、`main.ts:215` 開戰時的 `setWorld(w, −1)`，都整張）。
   - 城鎮照舊整個重建（城鎮快取以房子物件為鍵，複製世界之後全部拿不到；要改另開卡）。`tests/trenches-view.mjs:27`（`    this.trench118.sync(w, true);`）和 `tests/walls-view.mjs:36`（`buildTown(w).geometry()` 那一行）錨著的兩行原樣保留。
4. **閥** `?noR098=1`：三件都回到今天的做法（整張上傳、換段全部清、預覽整張重畫）。接在 `main.ts:82` 既有的那一行後面（`main.ts` 不多一行）。

## 風險

- **顯示卡的差別**：`copyTextureToTexture` 在 SwiftShader 與這台筆電的顯示卡上量過；別的手機可能不一樣——所以有閥。
- **鄰居影響屋頂高度**：挑錯時量的 4,554–5,718 個點 0 個不同，但那是兩張圖；驗收 3 每一次事件之後都比，真的有就把鄰居加進鍵。
- **三 r186 的細節**：暫存一旦被畫過或 `initTexture` 過，`copyTextureToTexture` 會走 GPU 複製、從空貼圖複製過來；`setTexture2D` 在 `needsUpdate` 時先整張傳。都寫成守衛。
- **量時間的雜訊**：這台筆電同一件事兩次可以差兩倍；用中位數與同一次量測的比例。
