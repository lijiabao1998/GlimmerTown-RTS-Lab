## 為什麼做這張

`tests/bombard-eligibility-browser.mjs`（R137）在同一個 Chrome 行程裡跑三個視口的開關對照、混合生產、實際陣亡（含低幀率）三段，期限 108 秒、子行程上限 120 秒。最近 CI 上這支在 unit 第 2 份跑 69–99 秒；本機單獨跑 main 83–106 秒。期限幾乎沒有餘裕，慢一點的 runner 就超時：

- #104（R905）`17d9021` 的 PR 那一輪連兩次（含重跑）紅在「operational deadline exceeded; not a semantic negative」，同一個提交的 push 那一輪 91 秒綠。紅的時候三個視口與混合生產的樣張都拍了，卡在實際陣亡那一段。
- 本機單獨跑：main 106、83 秒；R905 85、84 秒。R905 沒有變慢，是 main 本來就貼著期限。

R137 自己的卡面也記過一次：負控跑到 108 秒期限，當時的解法是把負控拆到另一個行程（`tests/bombard-eligibility-negative-browser.mjs`）。這張用同一個辦法拆正向那一半。

## 做什麼

1. `tests/bombard-eligibility-browser.mjs` 認一個新旗標 `--r137-death-only`：
   - 沒有旗標：照舊跑三個視口（1440／412／860）開關對照與混合生產（含它們的逃生閥對照）。
   - 有旗標：只跑實際陣亡兩段（開著＋低幀率、關著）與它們的逃生閥對照。
   - 兩邊都照舊檢查零頁面錯誤，結尾印出各自跑了什麼。
2. 新檔 `tests/bombard-eligibility-death-browser.mjs`：跟負控那支一樣，只加旗標再 import 主檔。
3. 斷言一句都不刪不改；108 秒期限、120 秒子行程上限、`bounded` 每步 8 秒都不動；負控那一半不動。

## 對其他車道的影響（照實寫）

- R137 是 GPT 車道的守衛，這張由 Claude 改它的分段方式，斷言內容不變。之後 GPT 改 R137 正向斷言時，要記得陣亡那段在新檔的行程裡跑。
- `tests/` 多一支檔，unit 分片的分配可能跟著挪；每份總時間大約多一次 vite 建置與 Chrome 開機（約 10–15 秒）。

## 不改什麼

- 產品程式、模擬、黃金雜湊 `eea1d59b`、`tools/unit.mjs` 的 120 秒上限、R137 的 108 秒期限都不動。
- 不放寬任何斷言、不跳過任何段落、負控不動。

## 施工紀錄

- `tests/bombard-eligibility-browser.mjs`：多一個 `deathOnly` 旗標。沒有旗標時跑原本的三視口迴圈與混合生產；有旗標時先 `viewport(412)`（原本陣亡那段也是在 412 跑，前一行就是 `await viewport(412)`），再跑 `liveDeath(false, true)`、`liveDeath(true, false)` 與它們的逃生閥對照。零頁面錯誤那句兩邊都跑。結尾的 OK 訊息寫出各自跑了什麼、花了幾毫秒。
- `tests/bombard-eligibility-death-browser.mjs`：五行，跟負控那支同一個寫法。
- 逐句比對：diff 只動了旗標宣告、兩行分支（`if (!deathOnly) {`、`} else { await viewport(412);` 與收尾的 `}`）、計時用的 `started0` 與 OK 訊息；`assert` 一句都沒動。主檔：三視口×開關的選取、長按、計數、版面、取消、兩種砲擊、Escape、重播、逃生閥對照；混合生產開關與它的逃生閥對照。新檔：實際陣亡（開著＋低幀率、關著）、低幀率回呼數、重播、逃生閥對照。兩邊：零頁面錯誤。負控那支一行沒動。

1. 本機單獨跑（`CI=1`，都綠）：
   - 主檔 67 秒（Chrome 段 65.7 秒）；拆之前同一台機器 main 83–106 秒。

2. 兩支正向都低於 108 秒期限：主檔約剩 40 秒，陣亡檔剩 85 秒以上。

   - 第一次改的是 `${counts.he}`，那是負控的錨點，兩支都在建置時就紅（「Build failed」），不算數；改用煙幕那一處重做。
4. CI：#105 綠（PR 那一輪 40732383168、push 那一輪 40732346191，兩輪 unit 裡三支 R137 都過）。
